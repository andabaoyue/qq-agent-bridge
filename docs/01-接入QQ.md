# 01 · 把 QQ 接进来

这一篇只做一件事：让 QQ 的消息能进到 `bridge/daemon.py`，让它能发出去。

## 你要准备的东西

1. 一个**能登录的 QQ 号**，专门给机器人用。不要用你的主号。
2. Windows 上的 QQ NT 客户端（NapCat 目前主要在 Windows 上成熟）。
3. 这台机器上能跑 Python 3.9+。

## 第一步：装 NapCat

[NapCat](https://github.com/NapNeko/NapCatQQ) 是一个 QQ NT 客户端插件，
它对外提供 OneBot v11 接口。我们只用它当"协议翻译层"。

它的安装方式会变，所以这里不给固定命令，去它的 release 页面拿对应
QQ 版本的包，按它的 README 走。装完能登进 QQ、且 WebUI 能打开，就算通了。

> 一句实话：这一步是整个流程里最容易出问题的一步，而且问题往往跟
> 这个仓库无关（QQ 版本更新导致 hook 失效之类）。如果卡在这里，
> 去找 NapCat 的 issue 区，比在这里查更有用。

## 第二步：配 NapCat 的网络

在 NapCat 的 WebUI（或配置文件）里配两样东西。

**A. HTTP 服务端** —— 让我们的 `step.py` 能发消息：

```
host: 127.0.0.1
port: 3000
```

**B. HTTP 客户端（上报）** —— 让 NapCat 把收到的消息推给我们：

```
url: http://127.0.0.1:5701
messagePostFormat: array
reportSelfMessage: true      ← 这个必须开，见下面
```

配置文件的形态大致是（不同版本字段名可能略有差异）：

```json
{
  "network": {
    "httpServers": [
      {"name": "http-server", "enable": true, "port": 3000,
       "host": "127.0.0.1", "messagePostFormat": "array"}
    ],
    "httpClients": [
      {"name": "http-client", "enable": true,
       "url": "http://127.0.0.1:5701",
       "messagePostFormat": "array",
       "reportSelfMessage": true}
    ]
  }
}
```

### 为什么必须 `reportSelfMessage: true`

因为这个开关决定「机器人自己发的消息会不会也被推一份回来」。

daemon 需要它，用来做**引用回复判定**：群友点「回复」针对 bot 的某句话
追问时，那条消息的原文里既没有 `@`、正文里也没写 bot 的名字 ——
如果不知道"被引用的那条是我发的"，这条追问就只能当闲聊丢掉。

daemon 会把收到的自己消息 id 记到 `workspace/self_message_ids.txt`
（只留最近 500 条），重启后能恢复。

**不开启的后果**：功能不会报错，只是「有人点回复追问 bot」这类消息会
莫名其妙的没反应。这种 bug 最难查。

### 为什么 `messagePostFormat` 要 `array`

我们的解析按 `message` 数组逐段处理（text / image / at / reply / face /
json 卡片）。`string` 格式会给一段 CQ 码字符串，这里的代码不解析它。

## 第三步：验证连通

先起 daemon：

```bash
python bridge/daemon.py
```

然后**用另一个号**（或者让朋友）给你的机器人发一句话，daemon 窗口应该出现：

```
--> [QQ PRIVATE] [identity: guest (...)] from 某人 (123456): 你好
```

同时 `workspace/daemon.log` 里也有同样一行（那是真正的日志，见文末）。

然后测发出去：

```bash
python bridge/step.py --reply "测试" --user_id 123456 --send-only
```

看到 `[SEND_OK] private 123456` 就成了。

> 第一次先给**自己的小号**发，别先发群。理由见下。

## 第四步：配群

默认配置里 `allow_groups` 是空的 —— **所有群都不理**。这是故意的。

打开 `bridge/config.json`：

```json
"group_filter": {
  "mode": "mention_only",
  "allow_groups": ["123456789"],
  "block_groups": []
}
```

- `allow_groups` 填你想让它参与的群号。填 `["*"]` 表示所有群都按规则处理。
- `block_groups` 里的群**一条都不处理**（不进队列、不存图、零唤醒）。

### 关于「要不要让它主动说话」

默认 `mode` 是 `mention_only`：只回被点名的（@ 它、提到 `bot_names`、
有人引用回复它、或者是主人自己说话）。

**强烈建议从 `mention_only` 开始。** 如果你配成 `mention_only_question`，
它会把任何带「怎么/为什么/有没有」的句子都当成在问它 —— 而群聊里
这种句子遍地都是。

实测过的代价：在一个 1500 人群里，一条「吃了吗」就能把它叫起来一次，
每次唤醒 = 一整个 LLM 请求。原版配置曾经用 `?` `？` `吗` `啥` `什么`
作为触发词，结果是一个人 5 分钟内问了三遍「醒了吗」，三次全都触发了。

**先小范围用，先挨一次"它怎么不回我"的抱怨，比先挨一次"这机器人在刷屏"的抱怨好。**

### 关于「有些群根本不想要 AI」

`block_groups` 就是为这个存在的。而且它做得比"不回"更彻底：
在解析图片之前就把整条丢掉，不存一张图、不留一条日志、不占一丝带宽。

有些群里，管理员会很客气地私信跟你说「麻烦别让它在群里说话」。
这种时候要做的不是"想办法不被发现"，而是**连读都别读**。

## 日志在哪

```
workspace/daemon.log            真正的日志（FileHandler，只追加，重启不覆盖）
workspace/pending_messages.json 还没被 Agent 取走的队列
workspace/last_target.json      上一条消息来自哪里（回复时的默认目标）
workspace/self_message_ids.txt  我们自己发的消息 id（引用回复判定用）
workspace/media_inbox/          收到的图片原件
workspace/.inject_token         注入口的 token（首次自动生成）
```

> ⚠️ 如果你按某些教程习惯把 stdout 重定向到文件（`python daemon.py > out.log`），
> 那个文件**会被下一次启动覆盖成 0 字节**。真正的日志是 `workspace/daemon.log`。
> 因为这个差别误判过一次「消息没发出去」。
