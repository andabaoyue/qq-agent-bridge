# 08 · 设计决策

这篇记「为什么这么设计，而不是那么设计」。每条都写「替代方案是什么、
为什么没选」，因为**代码只能显示选了什么，注释才能保留选的过程**。

---

## 一、为什么需要一个中间 daemon，而不是让 Agent 直接连 NapCat

### 替代方案

1. Agent 直接调 NapCat 的 HTTP API，自己处理事件
2. 中间放一个常驻的 Python 服务（现在的做法）

### 为什么选 2

**理由一：Agent 不能常驻。**

Agent 每次"醒来"都是一个完整的 LLM 请求。如果它自己轮询 NapCat，
那"检查有没有新消息"这个动作本身就烧 token —— 一分钟查一次，
一天 1440 次请求，其中 1439 次什么都没发生。

中间这层是纯 Python 的死循环，空闲时成本是 0。

**理由二：状态需要一个不进 LLM 上下文的住所。**

队列、许可票、自己发过的消息 id、冷却表 —— 这些是**进程状态**，
不是对话内容。放在 Agent 的上下文里既贵又不可靠（上下文会被压缩）。

**理由三：闸门必须是进程外的。**

如果许可判断和被判断的对象在同一个进程里，那等于没有判断。
Agent 改不了 daemon 的内存，这是闸门成立的前提。

### 代价

多一个要维护的进程，多一层要排查的环节。而且它是**单点**：
daemon 挂了，消息就在 NapCat 那边堆积或者丢掉。

这个代价是值得付的。没有它，安全模型无从谈起。

## 二、为什么队列落盘，但许可不落盘

这两件事看起来矛盾，其实是同一个原则的两面：**按"谁能改"来决定存哪。**

### 队列必须落盘

进程一停队列就没了 —— 实测因此丢过 3 条群友 @ 的消息，对方以为
Agent 看到了。重启后从 `pending_messages.json` 恢复是唯一解。

队列是**数据**，落盘无害。

### 许可必须只在内存

Agent 能读写文件系统。许可如果落盘，它写个 JSON 就自己给自己发了。

内存态的唯一改变途径是「真的收到一条符合条件的消息」。

### 这个区别的意义

不是"要不要持久化"的技术选择，是**信任边界**：
数据可以持久，权限不能。

## 三、为什么只对"声称是主人"的消息做真伪核验

### 替代方案

1. 不核验（早期就是这样，有洞）
2. 每条消息都核验
3. 只核验声称是主人的

### 为什么选 3

**不核验的问题**：`events_port` 是裸 HTTP。实测从同网段另一台机器
POST 一条 `user_id=<主人号>` 的假消息，200 返回，票开成了。

**全量核验的问题**：每条消息加一次 6ms 的往返。单看不多，但更要命的是
**NapCat 一旦抖动，所有消息都会被判成 `failed` 然后全丢掉** ——
为了防一个不存在的攻击面，把正常聊天全弄挂。这个交换不划算。

**只核验主人号**：冒充普通群友没有收益（本来就无权限），
而冒充主人是唯一有攻击动机的路径。**在有收益的地方加锁，没收益的地方不加。**

### 这是"按动机分配成本"，不是"按数量分配"

## 四、为什么"核验不了"不等于"假"

三种结果三种处理，其中第三种最需要解释：

| 结果 | 处理 | 理由 |
|---|---|---|
| `ok` | 正常放行 | — |
| `failed` | 整条丢弃 | 拿不出真 id，不可能是真消息 |
| 超时/连不上 | 不当主人，但按普通群友放行 | 见下 |

两种错误的代价不对等：

- 拒绝一条真消息 → 主人错失一次回复
- 错认一个假冒主人 → 把电脑交出去

**不对称的代价要求不对称的谨慎。** 模糊时往安全那边倒，但不把整条
消息扔掉 —— 万一真是主人，至少 Agent 还能回一句"我没拿到动手许可"。

## 五、为什么注入口单独一个端口，而不是复用长轮询口

### 替代方案

1. 复用 5702（长轮询口）
2. 新开 5703

### 为什么选 2

5702 默认绑 `0.0.0.0`，因为它要兼容"Agent 跑在另一台机器上"的部署。

如果把"能往队列里塞消息"的能力挂在 5702 上，等于**把写权限开出局域网**。

5703 只绑 `127.0.0.1`，再加一层 token。两把锁。

### 验证过的边界

```
无 token    → 403
错 token    → 403
空 text     → 400
错误路径    → 404
非本机来源  → 403
局域网地址连 → 连不上
```

## 六、为什么注入口不能开票

**这是整个设计里最重要的一条。**

`desktop_grant` 的语义是「主人在场」。

如果注入方（一个 AI）说话也能续票，那这个语义就废了：

- 它可以被群友话术骗
- 它可以被提示词注入
- 它的"在场"不等于主人的"在场"

一旦它能开票，「只有主人发消息才开门」这条就不成立。

### 实现

```python
msg = {
    "message_type": "inject",
    "user_id": -1,                  # 固定负数，不对应任何真人
    "permission": "inject",          # 强制
    "desktop_allowed": False,        # 强制
    "injected": True,
}
# 刻意不调用 _desktop_grant_msg
```

`-1` 这个值也是刻意的：永远不与任何真实 QQ 号冲突，日志里一眼能看出
"这不是人"。

### 验证过

```
注入前 granted = True
注入后 granted = True     ← 既没开也没关
```

自测里这一格是单独的断言：`injection does not change gate state`。

## 七、为什么日志记 `caller_source`

### 一开始的设计

只记 `caller`，从环境变量 `PHONE_CALLER` 读。

### 问题

**环境变量可以伪造。** 被调方设一个 `PHONE_CALLER=coder` 就能把责任
推给编码助手。那这个字段不但没用，还会**制造假证据**。

### 改后

记两个字段：

```json
{"caller": "agent", "caller_source": "env(conflicts-with-ppid:coder)"}
```

- `caller` = 自报的值
- `caller_source` = 怎么来的

**冲突时两个都留，不替人圆场。**

### 为什么父进程链更可信

因为**改不了**。要伪造得改进程树，那是另一个量级的操作。

### 一个技术细节

第一版按**进程名**匹配 `standby_listener`，实测永远判不出来 ——
因为它是 `python.exe standby_listener.py` 跑的，`Process.Name` 永远是
`python.exe`，脚本名只在 `CommandLine` 里。

必须把两者拼起来匹配。这个错差一点被自己糊弄过去（自检时标注了
"没实测，是推断"），实机一跑就现形。

## 八、为什么历史数据标 `unknown` 而不是猜

### 问题

早期记录没有 `caller` 字段。

### 替代方案

1. 根据时间戳推测（"那个时间段肯定是某人"）
2. 标 `unknown`

### 为什么选 2

**因为猜错过两次。**

- 说「08:17 没动过手机」—— 实际有
- 说「主动截图留证据」—— 实际全程只有 1 次 screenshot

**一个看起来确定的错误答案，比一个明确的「不知道」更有害。**
前者会让人停止怀疑。

### 实现

```
unknown(no-field)    49

WARNING: 这些记录无法确定是谁触发的 —— 别猜，猜错过两次。
```

## 九、为什么中文输入要「临时切、立刻切回」

### 替代方案

1. 一直把 ADBKeyboard 设为默认
2. 每次手动切
3. 自动临时切 + `finally` 切回

### 为什么选 3

**方案 1 的问题**：主人平时打字会看到一个只有提示条的空白键盘。
**这是侵占他的设备。**

**方案 2 的问题**：Agent 记不住要切，而且多一步就多一个出错点。

**方案 3**：`type_text` 内部自动处理，日志记
`via=ADBKeyboard(b64)（已自动切回原输入法）`。

### 为什么用 `finally`

如果广播抛异常而不切回，主人的输入法就一直是 ADBKeyboard。

**这是他第二天早上会遇到的第一个问题。** 一个原本为了"帮他"的功能，
变成了每天早上要修的故障。

## 十、为什么日志是 JSONL 不是数据库

### 理由

1. **追加写不会损坏**：一行一条，写坏了只坏一行
2. **人可读**：出问题直接 `Get-Content` 看
3. **不需要依赖**：不用 SQLite
4. **体积可接受**：一天一百多条，几十 KB

### 什么时候该换

超过 10 万条时全表扫描会慢。那时候再考虑 SQLite。

**现在不优化。** 一百多条不需要索引。

### 顺带一个教训

**不要用 PowerShell 的 `ConvertFrom-Json` 解析含中文的 JSONL** ——
一条失败可能整批吞掉。用 Python 逐行 `json.loads`，失败的单独报出来：

```python
for line in open(p, encoding="utf-8"):
    try:
        rows.append(json.loads(line))
    except Exception as e:
        print("parse failed:", e)   # 不要静默跳过
```

因为这个，漏看过整个 08:15–08:17 时段，误判「它没动过手机」。

## 十一、为什么群过滤默认只认点名

### 替代方案

1. 所有消息都处理（烧 token）
2. 按问句关键词触发（原方案）
3. 只认点名（现方案）

### 为什么放弃方案 2

实测日志：

```
18:58:00 「醒了吗」→ 触发
19:00:00 「醒了吗」→ 触发
19:02:57 「醒了吗」→ 触发（同一个人 5 分钟问了三遍）
```

原关键词表里有 `?` `？` `吗` `啥` `什么`。这些在群聊里密度极高：
「吃了吗 / 睡了吗 / 好看吗 / 你傻吗 / 去吗」全都命中；「你笑什么」
命中 `什么`；「人上身了？」命中 `？`。

**等于没有过滤。**

### 现方案

只认：`@` / 提到 `bot_names` / 引用回复它 / 主人本人。

想放宽就把 `mode` 改成 `mention_or_question`，但**先小范围用**。

> 「漏答一句没人会怪；乱答一句既烧钱又刷屏。」

## 十二、为什么冷却不丢弃消息

### 原做法

同一个人 15 秒内连发两条 → 第二条直接丢弃。

### 问题

「刚说完一句日常、紧跟着问的正事」被吞了，而且 Agent 完全不知道
有人问过。这类丢失最难发现 —— 没有任何错误日志。

### 现在

照常投递，带 `throttled: true` 标记。

**为什么让 Agent 自己决定**：因为只有它在上下文里，能判断"这条是不是
该等一下再回"。这个判断不该由 daemon 替它做 —— daemon 只知道时间差，
不知道说的是什么。

## 十三、没做的事（也是设计）

| 没做 | 为什么 |
|---|---|
| OCR | 装了就能逐条核对 Agent 说的每句话，但那样它不是在探索，是在应付考试 |
| 截图内容审计 | 同上 |
| 自动打标签 | 标签存哪、谁能改、会不会被绕过 —— 都没想清楚。不能先写进总结再补实现 |
| 内容过滤 | 同上 |
| 多设备支持 | 一次一台够用，加了复杂度没收益 |
| 语音合成 | 依赖链太长（TTS + 原生 silk 模块），留了接口没塞实现 |
| 表情包库 | 原版有，但那是一整套独立系统。这个仓库只保留"有个地方存图"的骨架 |

## 十四、如果要重做，会改什么

1. **配置从一开始就该外部化。** 原版把号码写死在源码里，要给别人用
   就得让他读代码才能配置。
2. **所有地址从一开始就该可配。** 写死一个 `127.0.0.1:3000` 让自测
   对着本机真实的 QQ 跑了一轮，日志上看起来完全正常。
3. **自测要起假的依赖，而不是依赖环境。** 现在补了 `FakeOneBot`。
4. **父进程链一次查全表，不要循环。** 第一版在循环里逐个查，
   单次 2504 ms，而每次 `log()` 都调它 —— Agent 每点一下手机，
   日志卡 2.5 秒。改成一次拿全表 + 内存里沿链走 + 60 秒缓存：
   `log()` 从 2500 ms 降到 0.3 ms。
5. **`status` 一开始就该写日志。** 它是唯一漏掉的，而"谁在什么时候
   看过我的手机"恰恰是最该留痕的操作。
6. **先查系统层（Windows 设备树）再查 adb。** 能早半小时定位
   「USB 调试没开」。

## 一句话总结这套设计的取舍

**代码不保护你，边界才保护你。**

那些看起来"多余"的检查（内存态的票、message_id 核验、注入方不能开票、
冲突时两个都留）每一条都对应一个具体的、发生过或差一点发生的失败。

删掉任何一条，代码都能跑，测试也可能过，但它就不再是这套东西了。
