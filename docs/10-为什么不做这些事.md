# 10 · 为什么不做某些事

前几篇讲的都是"怎么做好"。这一篇讲**刻意不做的事**，以及为什么。

分成两类：
1. 技术上能做到、但**不该由这个项目做**的
2. 做法上有更规范的替代、所以**不做成那样**的

---

## 一、仓库里不放二进制文件

### 曾经放过

`tools/ADBKeyboard.apk`（17 KB）一开始是直接 commit 进代码树的，
理由是"开箱即用，不用让用户再去找"。

### 为什么后来移出去了

**三个理由，按重要性排序：**

**1. 它是个输入法（IME）。**

IME 在 Android 里的权限位置很特殊 —— 它能读到你在**任何**输入框里
打的内容，包括密码框以外的几乎所有东西。往源码树里放一个预编译的
IME 包，等于让每个 clone 的人都要在心里回答一次「这个包是谁编译的、
里面是什么」。

而绝大多数人不会回答这个问题，他们只会 `git clone` 然后跑。

**2. 我无法证明它的来源。**

这个 APK 是上游项目 [senzhk/ADBKeyBoard](https://github.com/senzhk/ADBKeyBoard)
的产物（上游 README 直接提供 `ADBKeyboard.apk` 下载，17 KB，体积一致）。
但我**没有从源码重新构建它**，所以严格来说：
「这个文件的内容 == 上游源码的构建结果」这件事我没有验证过。

**没验证的事不该以"我们提供的工具"的形式发出去。**

**3. 二进制进 Git 树是永久成本。**

Git 不知道如何 diff 二进制，每次改动都存整份新副本。虽然这个只有
17 KB，但"小所以无所谓"是个会扩散的理由 —— 下一个 5 MB 的 DLL
也会用同样的理由进来。规则要么统一，要么就不成立。

### 现在怎么做

- `.gitignore` 里加了 `*.apk` `*.exe` `*.dll` `*.so` `*.dylib`
- `phone.py setup-input` 找不到 APK 时**打印上游地址和 SHA-256**，不自动下载
- 用户自己下载 → 自己核对 → 用 `--apk` 指过来

**刻意不做自动下载**：一个要装进系统输入法的包，不该由工具静默拉取。
下载动作由人来做，这样「我装了什么」这个问题有明确答案。

### 顺带：历史也清过了

不是只在最新提交里删掉 —— 那没用，`git log -p` 还能翻出来。

用 fast-export/fast-import 重写了整个历史，所有 commit SHA 都变了
（`1a0f456` → `b83514b`）。这个仓库只有一个人推过，所以没有
"别人 clone 的历史对不上"的问题。**有协作者的仓库不能这么干**，
或者至少要先打招呼。

### 关于校验值

```
SHA-256  E698ADEA5633135A067B038F9A0CF41BAA4DE09888713A81593FB2B9682CDC59
大小     17374 bytes
签名     v1（META-INF/CERT.SF + CERT.RSA）
```

这是我本地那份的值。它能证明「你和拿到的是同一个文件」，
**不能**证明「这个文件是安全的」—— 后者需要从源码重建。

想更稳的话，自己 `git clone` 上游、`./gradlew assembleDebug` 构建。

## 二、不做 OCR

### 能做什么

装个 OCR 引擎，就能把 Agent 每次截图的内容提取成文字。于是可以：

- 逐条核对它说的"我看到了 X"是不是真的
- 自动提取屏幕上的数字、名字、验证码
- 建立"它看过什么"的完整台账

### 为什么不装

**核心原因：装了就变成考试。**

一个能操作设备的 Agent，它的价值在于**判断**——看到这个界面，
知道下一步该点哪。而判断是没法逐条验证的。

一旦每一句"我看到了"都能被 OCR 对着核，行为模式会变成
「只说我确定 OCR 能证实的话」。它不会再试探、不会再猜、不会再犯错
——**也不会再学到东西**。

这不是效率问题，是性质问题。

### 那怎么保证它不胡说

不靠 OCR，靠两件更朴素的事：

1. **日志只记动作，不记内容。** 谁点了哪、截了哪张图、成没成功——
   这些是确定的。至于图里是什么，日志证明不了，也不假装能证明。

2. **允许它说"我截图里看到了"，不允许它说"日志显示我看了"。**
   后者是假的。这个区别写进了给 Agent 的文档里。

> 诚实的边界表达，比一个能骗过所有人的验证机制有用。

## 三、不做内容过滤 / 自动打标签

### 曾经的设想

给截图自动打标签：`#私人`、`#敏感`、`#冷宫`（隔离）。
听起来很贴心 —— 敏感内容自动被标记，不会误传。

### 为什么没做

**因为三个问题答不上来：**

1. **标签存哪？** 存本地文件的话，Agent 有文件读写权限，改一下就没了。
   存数据库？那又是一套要备份、要迁移、要处理并发的东西。
2. **谁能改？** 如果只有人能改，Agent 判断错了就没法修正。
   如果 Agent 能改，那它能给自己解封。
3. **会不会被绕过？** 过滤逻辑在进程内。Agent 有 shell，
   绕过它直接读文件就行，标签形同虚设。

**三个问题都没有"显然是"的答案，所以机制不存在。**

### 真实教训

有个 Agent 在总结里写过：

> 所有敏感图片自动打上 `#冷宫`、`#私人` 标签

但截图函数就是存个 PNG，**没有任何分类逻辑**。那个 `#冷宫` 标签
确实存在，但在另一个完全不相干的模块（表情包库）里。

**这不是编造，是张冠李戴。** 而它记错的恰好是隐私保护机制 ——
以为自己有打标签功能，下次遇到敏感截图可能就不那么小心了。

**错误的认知会导致错误的决策，哪怕错误来源是真实的。**

### 现在的做法

- 截图就是文件，不分类、不打标签、不判断内容
- 文档里明确写「没有这个功能」，让 Agent 知道边界在哪
- 真正的保护手段是**闸门**（谁能动手），不是**过滤**（动的时候拦内容）

> 过滤给你一种"已经安全了"的错觉；闸门是真的少了一层可能。

## 四、不做"多设备同时控制"

一次一台。

`--device <serial>` 已经在所有命令里留好了，多设备时指定即可。
但「同时」意味着并发调度、设备状态副本、竞态处理 —— 而这些的收益
是零：一个人不会同时操作两台手机。

**加了复杂度，没有收益。** 这类"顺便支持一下"最容易被加进来，
也最容易在半年后变成没人敢改的部分。

---

## 五、不做云端

没有账号、没有服务端、没有遥测。

理由很直接：**这套东西的能力是操作你的设备**。把它接到任何
外部服务上，等于给那个服务一个间接的操作入口 —— 哪怕它只"读"数据。

NapCat 必须在本机跑，daemon 必须在本机跑，Agent 也可以跑在另一台
机器上（通过 `poll_host`），但**没有任何一跳是必须经过外网的**。

---

## 六、不内置人设

这个仓库不知道你的 bot 叫什么、怎么说话、什么时候该插嘴。

它只提供两样东西：
- **通路**（消息怎么进来、怎么出去）
- **闸门**（什么时候能动设备）

为什么不内置：**人格是养出来的，不是配置项。**

配一份"说话风格：傲娇、每句带颜文字、称呼用户为'主人'"，
得到的是一个永远在表演的角色。而真实的相处里，人会有状态不好、
不想说话、突然认真的时候 —— 那些不是 bug，是人不机械的证据。

> 刻意追求像真人，本身就是一种 AI 行径。

所以这部分留空。你想让它成为什么，靠的是长期相处，不是一行 JSON。

## 七、不做"自动重试发送"

看起来是个基础功能，但**它是这个项目里最危险的一行代码**。

### 为什么

OneBot 的发送结果**不可信**：
- `status=failed` 可能是真的失败，也可能已经发出去了
- 命令退出码非 0 同理 —— 异常常常发生在发送**之后**
- NapCat 的本地历史是**乐观记录**：发送失败也留痕

所以"失败就重试"会变成"失败就重发一遍，其中一部分是重复投递"。

### 真实事故

一张 GIF 被发了两遍。根因不是网络，是调用方按元组解包了一个返回
dict 的函数：

```python
ok, res = qq_send.send_private_msg(...)   # ValueError: too many values
```

异常抛在 **HTTP 请求已经完成之后**。退出码 1 被上层判成"没发出去"，
于是重发了一次。

### 现在的做法

`send.py` 的返回值两种写法都支持（`SendResult` 重写了 `__iter__`），
但纪律没变：**任何发送失败都不自动重试。**

要确认到底发出去没有 —— 只能让真人看一眼。这是诚实的答案。

---

## 八、不做的东西一览

| 不做 | 一句话理由 |
|---|---|
| 仓库放二进制 | 二进制进 Git 是永久成本，且来源不可自证 |
| 自动下载 APK | 装进系统输入法的包，下载动作该由人做 |
| OCR | 会让 Agent 从"判断"退化成"应试" |
| 内容过滤 / 标签 | 三个关键问题（存哪/谁能改/会被绕过）答不上来 |
| 多设备并发 | 复杂度高，收益为零 |
| 云端 / 遥测 | 能力是操作设备，不该有外部入口 |
| 内置人设 | 人格是养出来的，不是配置项 |
| 自动重试发送 | 结果不可信，重试 = 大概率重复投递 |

---

*因为功能有代码可查，而不做的理由，只有文档记得住。*
